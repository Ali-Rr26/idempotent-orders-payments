1. Solución

Dos servicios Flask independientes, cada uno con su propia base SQLite. Ambos se ejecutan en local (dos terminales) o con docker compose up --build; las instrucciones completas están en el README del repositorio.

Postman ──► Order API :5000 (orders.db) ──► Payment Mock API :5001 (payments.db)
  • Order API: recibe el pedido con un header Idempotency-Key, reserva el stock y crea el pedido en una sola transacción. Después cobra al mock y expone el estado del pedido. Tablas: products, orders (clave UNIQUE), reservations (una por pedido, UNIQUE).
  • Payment Mock API: registra un cobro por clave (payment_key UNIQUE) y simula tres modos. approve y reject responden de inmediato. timeout hace commit del cobro y luego tarda 5 s en responder; la Order API corta a los 2 s. Expone GET /payments/{key} para consultar el resultado.
  • La clave de pago es estable: payment_key = "pay-" + Idempotency-Key. Si la Order API reenvía el cobro, el mock devuelve el registro existente y no crea otro.
  • Los errores usan el formato estándar RFC 9457 (application/problem+json) con un mensaje explicativo; por ejemplo, el 422 cuando se reutiliza una clave con otro cuerpo.

Estados del pedido

EstadoSignificadoReserva
PENDING_PAYMENTPedido creado y stock reservado; el cobro está en curso.RESERVED
PAYMENT_UNCERTAINLa respuesta del pago se perdió (timeout, error de red o 5xx). No se sabe si hubo cobro: hay que consultar al mock, no volver a cobrar.RESERVED
PAIDFinal. Pago aprobado (directo o tras reconciliar).CONSUMED
REJECTEDFinal. PAYMENT_REJECTED: pago rechazado, stock devuelto una vez. OUT_OF_STOCK: no había stock, sin reserva ni cobro.RELEASED / ninguna

Los estados finales nunca se sobrescriben: todos los UPDATE de estado llevan WHERE status IN ('PENDING_PAYMENT', 'PAYMENT_UNCERTAIN').

5. Conclusión

¿Qué estado persistieron para recuperarse?

En orders.db guardamos la Idempotency-Key (única), el hash del cuerpo, el estado del pedido (incluido el estado intermedio PAYMENT_UNCERTAIN), la payment_key estable derivada de la clave y la reserva con su propio estado (RESERVED / CONSUMED / RELEASED). En payments.db, el mock guarda el resultado de cada cobro bajo su payment_key única, y hace commit antes de responder. Con eso, después de una respuesta perdida o un reinicio, la Order API sabe qué pedidos quedaron abiertos y a qué clave preguntar: consulta GET /payments/{payment_key} y aplica el resultado guardado, en lugar de volver a cobrar a ciegas.

¿Cómo comprobaron que no hubo efectos duplicados?

En tres niveles:

  1. Restricciones en la base: UNIQUE en orders.idempotency_key, reservations.order_id y payments.payment_key; CHECK (stock >= 0).
  2. Updates condicionales: stock = stock - q WHERE stock >= q para reservar, y WHERE status = 'RESERVED' para que la compensación devuelva stock una sola vez.
  3. Verificación: 99 assertions de Postman, que comprueban mismo id, header de replay, stock y cantidad de cobros después de cada reintento. Además, las consultas GROUP BY … HAVING COUNT(*) > 1 y la de inconsistencias devuelven 0 filas, y las pruebas de concurrencia producen un solo pedido y un solo cobro.
No prometemos "exactamente una vez" en la red: un cobro puede enviarse más de una vez. Garantizamos como máximo un efecto por clave y que el estado real siempre se puede averiguar después de una falla.
